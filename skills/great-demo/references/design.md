# Demo Design

How to build a demo from prospect context using the Great Demo! method.

## What You Need Before Drafting

Six inputs. If any are missing, ask the user before proceeding. Do not invent them.

1. **Audience**: each person's name, title, role, decision authority
2. **CBI per stakeholder**: the Critical Business Issue each person owns
3. **Reason per CBI**: why they can't currently solve it
4. **Specific Capabilities to demonstrate**: the agreed list, mapped to CBIs
5. **Time budget**: total minutes for the demo segment
6. **Demo objective**: Technical Proof (prove specific capabilities to close the technical sale) or Vision Generation (help customer envision the solution). Cohan rules out Information demos as too risky.

If the user has only some of these, build what you can and flag the gaps explicitly. A demo built without a CBI is a feature parade in disguise.

## The Screen Map

The core of the plan is a map from each stakeholder's pain to the screen that answers it.

| Stakeholder | CBI | Reason | Specific Capability | Screen to show | The Delta |
|---|---|---|---|---|---|

Rules:

- One screen per pain. If you can't name the CBI a screen addresses, cut it.
- Name each screen and object exactly as it appears in the product or tenant.
- Prefer a screen that shows an outcome the audience already wants (the completed report, the finished invoice, the rendered dashboard, the cleared-out alert queue) over a tour of a capability. If the user proposes a generic feature screen, push back: show the outcome, not the capability.
- Order by priority of pain, with the most senior stakeholder's pain first when the Chain of Pain allows. Put what matters most in front of the audience early.
- Signs a screen is landing: the audience leans in, asks how, asks if it will work with their data. Signs it is not: nods, polite questions, "interesting" with no follow-up.
- State the Delta the screen supports in money, time, or people. If the customer's numbers are missing, say so and list the questions that would produce them.

For Technical Proof demos, use the customer's actual situation from qualification. For Vision Generation demos, use a Reference Story (a sanitized situation from a past success with the same job title at a different company). If the audience reacts strongly to a Reference Story, pivot to their own situation and qualify before continuing.

## Showing the Path

How each screen gets reached matters as much as the screen.

- Count the clicks and reduce them. Every click the audience sees is a step they think they'll have to perform.
- Organize demo files in top-level directories or on the desktop. Burying a file under five folders adds five clicks the audience will remember.
- Use the customer's name or company name in file names. Never "demo," "test," "demo1," "demo2."
- Never use keyboard shortcuts. The audience needs to see menu choices to envision themselves doing it.
- Go deeper only where the audience asks or a Specific Capability needs it. Don't drift into unrelated features just because they're cool.

A useful axiom: the first demo to a customer generates a set of questions, and the second demo to a similar audience generates roughly 80 percent of the same ones. Keep them as material for the next plan.

## Questions and Meeting Check

Plan where questions get answered. Park the ones that would pull the demo off its path (see `delivery.md` for the Not Now List) and leave time for them.

At the start of the meeting, confirm what the customer wants to accomplish and what their time constraints are, even if you already know. Things shift between the meeting agreement and the meeting itself. If someone else already covered this in the introduction, confirm it instead of asking again.

## Timing

Give each section a time and total them against the budget the user gave.

If the plan is too long: trim depth first, then drop lower-priority Specific Capabilities. If it is too short: confirm every screen answers its pain and nothing got skipped. If everything is covered, leave it alone. Audiences appreciate meetings that finish early.

## Practice and Rehearsal

The amount of practice should be proportional to the deal value.

- Time it without questions, then add Q&A buffer.
- Run a full rehearsal with the Selling Team. Other team members play audience and surface gaps.
- Take rehearsal feedback. Make agreed changes. Resist the urge to add capabilities. Stay focused on the agreed Specific Capabilities.
- Confirm infrastructure with the customer before traveling. Ask: have meeting objectives changed, are there new audience members, are there new time constraints?

## Worked Example: Designing from Sparse Inputs

User says: "Help me design a 30-minute demo for the VP of Operations at a regional hospital. Their CBI is reducing time-to-diagnosis in the ED."

What to do:

1. Confirm what's known and what's missing. Known: audience (VP Ops), time (30 min), CBI (reduce time-to-diagnosis). Missing: Reason behind the CBI, Specific Capabilities, demo objective, other stakeholders.
2. Surface the gaps. Ask the user to fill in the Reason and the Specific Capabilities, or propose plausible defaults and flag them as assumptions.
3. Once filled in: build the screen map (job title, CBI, Reason, Specific Capability, the screen to show, the Delta). The screen is probably the patient throughput dashboard or a triaged-case view. Sketch the path to it in click-count terms. Give each section a time against the 30-minute budget.
4. Output: a plan with timing, the screen map with the reason for each choice, what was cut, the questions likely to be parked, and how the Delta will be stated.

Don't draft an entire 30-minute monologue. Output the plan with talking points. The user's voice fills in the language during delivery.
